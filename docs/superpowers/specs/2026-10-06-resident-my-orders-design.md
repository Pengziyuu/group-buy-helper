# 住戶「我的訂單」、已訂標示與結單日期：設計

**日期：** 2026-10-06
**狀態：** 已與團主確認（2026-10-06），實作中

## 背景與目標

住戶反映想一次看到自己在所有團購的訂單。現在只能一團一團點進去看，也看不出自己在哪幾團下過單。另外，已結單的團只顯示「已結單」，看不出是哪一天結的。

目標：
- 住戶在團購列表一眼看出**自己訂過哪幾團**、每團**有多少人下單**，卡片不能因此變得忽高忽低或擠滿字。
- 新增**「我的訂單」頁**：列出自己在每一團訂了什麼、多少錢、這團現在的狀態。
- 已結單的團顯示**實際結單日期**。

**成功標準：**
- 住戶打開列表，不用點進任何一團，就知道哪幾團自己已經訂了。
- 住戶在「我的訂單」頁看得到每一團的品項、數量、金額和合計，開團中的團可以直接回去修改。
- 已結單的團在住戶列表、住戶團購頁、我的訂單、團主列表都顯示「M/D 結單」。
- 住戶只看得到自己的訂單；其他戶只會變成「N 人」這個數字。

## 已確認的決策

| 決策 | 結論 |
|---|---|
| 「已訂 N 包」的意思 | 自己訂了多少，不是整團總數（整團總數已經是「62 個 / 100 個」） |
| 列表卡片上的「自己已訂」 | 縮圖左下角的小標籤「已訂 4」，有訂才出現，卡片高度不變；列表不顯示金額 |
| 列表卡片上的「下單人數」 | 接在原本的數量後面：「62 個 / 100 個・18 人」，不另外佔一行 |
| 「我的訂單」入口 | 底部分頁列「團購／我的訂單」，只出現在這兩頁；團購下單頁不顯示（那頁底下已有送出按鈕列）。電腦版寬度 ≥ 1024px 時改放在上方標題列 |
| 我的訂單卡片 | 左邊放商品縮圖（和列表同一張）、團名、狀態、時程，下面是品項明細與合計；開團中顯示「修改訂單 ›」，已結單顯示「查看 ›」，都連到該團頁面 |
| 結單日期 | 同一批一起做，資料庫記錄每團實際結單的時間 |

## 畫面細節

### 團購列表（`ResidentCampaignListApp`）

- **縮圖標籤**：自己這團訂的正式品項數量 > 0 時，顯示「已訂 N」，不加單位，避免標籤變長。只訂了額外品項（數量不計入）時，顯示「已訂」，不帶數字。沒有圖片的團一樣疊在「無圖片」框的左下角。
- **人數**：只算「有訂東西的戶」，包括只訂額外品項的戶。清空訂單後留下的空訂單不算。0 人時不顯示「・0 人」。
- **已結單卡片**：時程那行目前只剩「貨到通知」這類到貨資訊，前面加上「10/3 結單」。

### 我的訂單（新頁面，路徑 `/orders`）

- 依開團時間由新到舊排，開團中的排前面（和列表一致）。
- 每張卡片：
  - **縮圖**：48px。
  - **團名＋狀態標籤**：開團中／已結單。
  - **時程**：開團中顯示結單時間與到貨；已結單顯示「M/D 結單」與到貨。
  - **品項明細**：「品名 × 數量　$小計」，小計用下單當下記下的單價。
  - **額外品項**：「品名 +數量・另計」，沒有金額。
  - **合計**：「合計 N 單位・$金額」，單位用該團的數量單位（個、包、盒…）。
- 品項不顯示 A、B 代號（和 #18 複製數量拿掉代號一致）。
- 沒有任何訂單時：空狀態「還沒有訂單」，說明「在團購頁下單後會出現在這裡」，附「看看團購」按鈕回列表。
- 只顯示有內容的訂單，空訂單不列。

### 底部分頁列

- 兩個分頁：「團購」（購物袋圖示）、「我的訂單」（收據圖示），目前所在的那頁用主色。
- 固定在畫面底部，留出 iPhone 底部安全區域；頁面內容底部加同高度的留白，避免最後一張卡片被擋住。
- 在 LINE 裡打開時，LINE 自己的標題列在上方，下方沒有東西，不會衝突。

### 結單日期顯示的其他位置

- **住戶團購頁的「結單」格**：目前寫「已結單」，和上面的狀態標籤重複，改成「10/3」。
- **團主團購列表的「結單」欄**：已結單的團顯示「10/3 結單」。
- **舊的團查不到結單時間時**：維持現在的顯示方式（住戶端「已結單」、列表不顯示結單那格），不會顯示錯的日期。

## 資料與權限

### 1. 記錄結單時間：`campaign.closed_at`

- 新增欄位 `campaign.closed_at timestamptz`，可以是空的。
- 加一個資料庫觸發器，在團購狀態改變時自動填寫：
  - 從「開團中」變成「已結單」（或舊的「已到貨」）時，填入當下時間。
  - 重新開團時清空。
- **為什麼用觸發器**：結單有三條路，團主手動結單、時間到自動結單、額滿自動結單。觸發器一次涵蓋三條，以後新增別的結單方式也不會漏記。
- **舊資料補值**（只補查得到可靠時間的）：
  1. 有自動結單通知紀錄的團 → 用那筆通知建立的時間。
  2. 否則，若有設定結單時間且已經過了 → 用設定的結單時間，因為排程每分鐘檢查，誤差在一分鐘內。
  3. 其他（團主手動結單的舊團）→ 留空，畫面照「查不到」的方式顯示。

### 2. 列表多回傳四個欄位：`list_resident_campaigns()`

| 新欄位 | 內容 |
|---|---|
| `my_quantity` | 自己這團訂的正式品項數量合計；沒訂是 0 |
| `my_has_order` | 自己這團有沒有訂東西（含只訂額外品項） |
| `order_household_count` | 有訂東西的戶數 |
| `closed_at` | 結單時間 |

- 「自己」= 目前登入的 LINE 帳號綁定的那一戶（`customer.auth_user_id = auth.uid()`）。一個 LINE 帳號只會綁一戶，資料表本來就保證這點。
- 人數只是一個數字，不會帶出任何戶號或名字。住戶本來就能在團購頁的訂單牆看到誰訂了，所以這不算新增揭露。

### 3. 新增查詢：`list_my_orders()`

- 只回傳**目前登入住戶自己**的訂單，每筆包含：
  - 團購：代碼、團名、狀態、縮圖、數量單位、結單設定與到貨說明、`closed_at`
  - 正式品項明細：品名、數量、下單時的單價，依品項原本的排序
  - 額外品項
- 和其他住戶查詢一樣：只開放給已登入的住戶，未登入一律拒絕；並且只列出住戶所屬社區、已開團的團購，和列表的條件相同。
- 沒綁戶號的住戶回傳空的，不報錯，畫面顯示空狀態。

## 部署順序

這批改動對舊的前端相容：舊前端不讀新欄位，也不會呼叫新查詢。照 `docs/AI_AGENT_HANDOFF.md` 的規則：

1. 合併前先在本機和 CI 跑完資料庫檢查。
2. 合併後**先上線資料庫 migration**，再讓前端部署生效。
3. 上線後到正式資料庫讀回確認：新欄位存在、舊團補值的數量合理、兩個查詢的權限正確。

列表查詢的回傳欄位改變，需要先刪掉再重建。這會在同一個 migration（同一個交易）裡完成，中間不會有查不到的空窗。

## 測試

- **資料庫（CI 會跑）**
  - 三種結單方式都會填 `closed_at`，重新開團會清空。
  - 住戶 A 呼叫 `list_my_orders()` 拿不到住戶 B 的訂單；未登入被拒絕；沒綁戶號回傳空的。
  - 列表的 `my_quantity`、`order_household_count` 正確：空訂單不算人數，只訂額外品項的算人數但數量是 0。
  - 補值規則：有通知紀錄的、有過期結單時間的、手動結單的舊團各一筆，結果符合上面三條。
- **前端**
  - 縮圖標籤有訂才出現，只訂額外品項顯示「已訂」，卡片高度不變。
  - 0 人時不顯示人數。
  - 我的訂單：明細、小計、合計、額外品項「另計」、空狀態、開團中和已結單的連結文字。
  - 底部分頁列：所在頁面標示正確，在團購下單頁不出現。
  - 查不到結單時間時沿用原本的顯示。
- **示範模式**：示範資料補上「自己的訂單」與結單日期，PR 預覽看得到完整畫面。「只訂額外品項」的情況由單元測試與資料庫測試涵蓋，示範資料沒有另外做。
- **截圖**：手機和電腦寬度都截圖檢查，不可以出現水平捲動。

## 不在這次範圍

- 付款狀態：團主決定付款在系統外處理，我的訂單不顯示「已付款」。
- 領貨狀態：系統目前沒有記錄住戶是否已領貨。
- 一戶多個 LINE 帳號共用：資料表目前一戶只能綁一個帳號，不在這次調整。
